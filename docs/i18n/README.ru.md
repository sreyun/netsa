# netsa

**Платформа с открытым исходным кодом для ситуационной осведомлённости в сетевой безопасности и анализа поверхности атаки**

Превращает журналы веб-серверов, межсетевых экранов / IDS, сетевых потоков, аутентификации и процессов на хостах и DNS в картину безопасности, которую можно отследить, по которой можно действовать и которая продолжает учиться.<br>
Один исполняемый файл, готов к работе сразу, в том числе в изолированных сетях.

## Почему netsa

- **Без зависимостей, развёртывание в один шаг**: один исполняемый файл на Go со встроенным веб-интерфейсом, картами мира и провинций и городов Китая и офлайн-базами геолокации. Не нужны ни Elasticsearch, ни Kafka, ни база данных. Образы Docker доступны для amd64 и arm64, а при отключённом онлайн-отслеживании система полностью работает без сети в изолированных средах.
- **Не нужно заранее подгонять журналы**: автоматически распознаёт более 50 форматов, включая nginx / Tengine / OpenResty / APISIX / Kong / Apache / IIS / Caddy, WAF вроде ModSecurity, iptables, Huawei, H3C, FortiGate, Palo Alto, Suricata, аутентификацию Linux и Windows, распространённые DNS-серверы, Zeek, NetFlow / sFlow / IPFIX, журналы хостов Sysmon / auditd / Wazuh, журналы входа в приложения, а также форматы-обёртки сборщиков вроде Docker и Filebeat.
- **Точное обнаружение, оповещениям можно доверять**: 87 сигнатурных правил (часть адаптирована из OWASP CRS), синтаксический анализ libinjection и поведенческое обнаружение; ответы, свидетельства сеансов и уязвимости активов используются для повторной проверки «видимого успеха». Уровень опасности определяется единым централизованным решением: заблокированная атака никогда не помечается как «критическая», а успешная эксплуатация не будет пропущена.
- **Знает китайские OA-системы и промежуточное ПО**: 261 встроенная сигнатура уязвимых конечных точек для 42 продуктов, включая OA-системы Seeyon, Weaver, Yonyou, Tongda, Landray и Wanhu, FanRuan, Esafenet, RuoYi, Nacos, APISIX, Nginx UI, а также оборудование Sangfor, Ruijie, Hikvision и Dahua. В оповещениях сразу указываются продукт и идентификатор CVE / CNVD; уязвимые конечные точки, которыми пользуется обычный бизнес-трафик, изучаются автоматически и перестают вызывать оповещения.
- **Разведданные: точность важнее объёма**: данные об IP-адресах, доменах, отпечатках TLS и хешах файлов (STIX / TAXII / MISP / текстовые списки), классифицированные по категориям (C2, вредоносное ПО, фишинг, майнинг, источник атак), с автоматическим отсевом злоупотребляемых публичных платформ. Точность каждого источника автоматически оценивается по вердиктам аналитиков, а источники с постоянными ложными срабатываниями автоматически понижаются.
- **Связь журналов межсетевого экрана и веб-сервера**: внутренний хост, который после веб-атаки подключается к атакующему или к адресу обратного вызова из полезной нагрузки атаки, помечается как скомпрометированный; подключение к адресу из полезной нагрузки доказывает, что она была выполнена.
- **Отслеживание до города, связь с группой**: восстанавливает реальный IP за CDN и прокси, обнаруживает подделку XFF и прямые подключения к исходному серверу в обход CDN. Несколько источников геолокации сверяются между собой с указанием уровня достоверности. Корреляция по общему происхождению и объединение в кампании находят сменяемые адреса выхода одного атакующего (одинаковый отпечаток инструмента, один идентификатор корреляции OAST, отпечаток TLS, один токен-приманка). Срабатывание [приманки](../detection.md#诱饵) (путь, токен, учётная запись-приманка или ханипот) с высокой уверенностью указывает на атакующего. Цепочка атаки на актив в хронологическом порядке показывает, как сервер сканировали, эксплуатировали, захватывали и использовали для горизонтального перемещения.
- **Чем дольше работает, тем точнее**: учится на вердиктах аналитиков. Правила и конечные точки с повторяющимися ложными срабатываниями автоматически понижаются, а подтверждённые атакующие при возвращении автоматически повышаются. Не нужно вручную вести списки разрешённого: система изучает по обычному трафику привычные значения каждого параметра и пассивно определяет продукты и фронтенд-фреймворки каждого сайта, поэтому обычный текст в поле поиска или зондирование продукта, которого на сайте нет, больше не вызывают оповещений высокой опасности. ИИ-сортировка поддерживает API OpenAI и Anthropic, так что можно подключить и локальный vLLM, и облачные модели. Она автоматически учитывает различия между моделями и по вердиктам аналитиков оценивает, насколько можно доверять каждой из них.
- **Полный цикл операций безопасности**: объединение в инциденты со сроками обработки, подавление ложных срабатываний, уведомления в DingTalk / WeCom / Feishu, связь активов и уязвимостей, хранение исходных журналов с пакетом доказательств в один клик, еженедельные и ежемесячные отчёты, самооценка по MLPS 2.0 (китайской многоуровневой системе защиты) и защищённая от подделки цепочка аудита.
- **Быстро на одной машине**: около 460 000 событий в секунду от начала до конца на машине разработчика (i7-10700, 16 потоков). Предварительная фильтрация Aho-Corasick почти избавляет обычные запросы от регулярных выражений, около 3 мкс на событие.

## Быстрый старт

### Попробуйте одной командой (симулированные журналы атак уже включены)

```bash
git clone https://github.com/sreyun/netsa.git
cd netsa
docker compose -f docker-compose.demo.yml up -d --build
```

Откройте <http://localhost:8080> и войдите как `admin` с паролем `Netsa@demo2026`. Симулятор непрерывно генерирует журналы атак, а панель обновляется в реальном времени.

### Развёртывание в продакшене

```bash
git clone https://github.com/sreyun/netsa.git
cd netsa
docker compose pull
docker compose up -d
```

- Откройте `http://<IP-сервера>:8080`. Начальный пароль находится в журналах: `docker compose logs netsa | grep 初始密码` (`初始密码` — это дословный текст журнала, означающий «начальный пароль»). Его нужно сменить при первом входе.
- По умолчанию читаются каталоги `/var/log/nginx` и `/var/log` хоста; syslog с сетевых устройств отправляйте на `<IP-сервера>:5514` (UDP / TCP).
- Чтобы зафиксировать версию, изменить порты или включить архив оповещений, сначала выполните `cp .env.example .env` и отредактируйте файл согласно комментариям.
- Windows PowerShell 5.1 не поддерживает `&&` и `grep`: выполняйте команды по одной и используйте `Select-String` вместо `grep`.

Об обновлении и откате, развёртывании без сети и частых вопросах см. [руководство по развёртыванию](../deployment.md).

### Анализ существующих журналов без развёртывания

```bash
go build -o bin/netsa ./cmd/netsa
./bin/netsa analyze /var/log/nginx/access.log* /var/log/ufw.log -o report.json
./bin/netsa analyze -listen :8080 access.log    # после анализа открыть панель
```

## Как это работает

```text
Источники журналов       nginx · межсетевой экран / IDS · Zeek · аутентификация и процессы хостов · вход в приложения · DNS · контейнеры и сборщики
   │                     отслеживание файлов / пакетный анализ / syslog (UDP · TCP · TLS) / сбор потоков (NetFlow · IPFIX · sFlow)
   ▼
Распознавание формата    формат и часовой пояс определяются отдельно для каждого источника и каждого отправителя
   ▼
Реальный IP              восстанавливает источник через доверенные прокси, отмечает подделку XFF и обход CDN
   ▼
Обнаружение угроз        сигнатурные правила (AC-префильтр + regex) + синтаксический анализ (libinjection) + правила для процессов хоста + поведенческое обнаружение (временные окна, ограниченная память)
   ▼
Разведданные и приманки  данные об IP / доменах / отпечатках TLS / хешах файлов; срабатывание путей, токенов, учётных записей-приманок и ханипотов подтверждает атакующего
   ▼
Фильтр свидетельств      свидетельства сеансов и сопоставления DNAT отсеивают зондирование, не дошедшее до сервисов; применяется подавление
   ▼
Изученная настройка      обычные значения параметров и продукты сайтов перепроверяют срабатывания; повторяющиеся ложные срабатывания понижаются по вердиктам аналитиков, подтверждённые источники повышаются (learn)
   ▼
Корреляция               связывает предыдущие веб-атаки: обратные вызовы и загрузку полезных нагрузок после атаки, последующие горизонтальные подключения скомпрометированных хостов
   ▼
Решение об опасности     нижняя граница категории, повышение при успехе и верхняя граница по результату определяют итоговый уровень опасности (risk)
   ▼
Хранилище состояния      профили атакующих · оповещения · инциденты · кампании · цепочки атак на активы · поверхность атаки · временные ряды · сохранение снимков
   │
   ├── Веб-панель и REST API (передача в реальном времени через SSE)
   ├── DingTalk / WeCom / Feishu / Webhook
   ├── Хранение исходных журналов · архив PostgreSQL (по желанию)
   └── ИИ-сортировка (по желанию, выводы записываются в карточку инцидента)
```

Ключевые принципы:

- **Уровень опасности решается в одном месте**: уровень, объявленный правилом, — лишь предложение. Так каждый этап не прибавляет и не вычитает уровень по-своему, и похожие события не получают разную опасность. См. [решения об уровне опасности](../detection.md#威胁等级判定).
- **Свидетельства важнее видимости**: «разрешено» межсетевого экрана, ответ 200 или успешный вход после серии неудач повторно проверяются по сеансам, эталонным ответам и признакам учётных записей.
- **У обучения есть границы**: калибровка правил учится только на вердиктах людей. Автоматическая настройка меняет уровень не более чем на одну ступень за раз, а успешная эксплуатация по-прежнему считается критической. Обычные значения параметров и продукты сайтов, изученные по трафику, понижают срабатывание только при одновременном выполнении двух независимых условий (параметр обычно содержит простой текст, и синтаксический анализ не находит инъекции; на сайте нет этого продукта, и запрос не был успешным), и только до низкой опасности, никогда не скрывая оповещение. Подавление ложных срабатываний, которое скрывает оповещения, должен принять человек. Выводы ИИ не используются как обучающие примеры и никогда не запускают автоматическую обработку.
- **Под нагрузкой не теряет контроль**: разбор и обнаружение выполняются параллельно и сохраняются пакетами, у числа профилей и окон обнаружения есть жёсткие пределы, а одна некорректная строка журнала не влияет на работу сервиса. Для накопления и отбрасывания в очередях есть метрики мониторинга.

## Разработка

Требуется Go 1.26 или новее (выпускные версии собираются Go 1.27). Чистый Go, без CGO.

```bash
go build -o bin/netsa ./cmd/netsa
gofmt -l internal cmd     # не должно ничего выводить
go vet ./...
go test ./...
```

Для тестов на гонки данных нужен компилятор C. Если gcc на машине нет, запустите их в контейнере:

```bash
docker run --rm -v "$PWD":/src -w /src golang:1.27-alpine sh -c 'apk add --no-cache gcc musl-dev && CGO_ENABLED=1 go test -race -short ./...'
```

Структура кода и процесс выпуска описаны в разделе [разработка и выпуск](../development.md).
